# PRD "拆弹"器

专业的产品需求文档分析 Skill，对 PRD 进行全面"拆弹"——识别逻辑矛盾、遗漏场景、优先级冲突和隐含假设，结合技术兼容性和前沿技术补充分析，输出专业诊断报告。

## 核心流程

### 阶段1：文档摄入与解析

**1.1 检测文档格式并解析**

- 本地文件（.docx/.pdf/.txt/.md）：使用 Read 工具读取
- 飞书文档链接：使用 lark-doc MCP 获取内容
- 粘贴文本：直接分析

**1.2 检测多模态内容**

检测文档中是否包含图片引用（流程图、架构图等）。

**IF** 检测到图片内容 **AND** 当前模型不支持多模态理解：

使用 AskUserQuestion 工具向用户提问：
```
问题：检测到文档包含图片/流程图等视觉内容，建议使用支持图片理解的多模态模型以获得完整分析。

选项：
A. 跳过图片分析，仅解析文本内容
B. 我会切换到多模态模型后重新提交
C. 其他：______
```

**1.3 引用检测**

扫描文档中的外部引用，提取引用清单供后续确认。

---

### 阶段2：文档理解与结构梳理

**完整阅读文档后，自主提取以下信息（不先问用户）：**

- 产品类型和业务领域
- 目标用户（从文档中识别）
- 核心业务场景
- 功能模块和技术方案
- 项目阶段（是否分期）
- 系统定位（独立产品/子系统）

**标准 PRD 结构对比：**

参考 `references/prd-structure-template.md`，诊断文档完整性。

**输出文档理解摘要：**
- 文档识别的基本信息
- 核心内容提取结果
- 文档结构评估
- 检测到的引用文件清单

### 阶段3：智能提问（条件触发）

**只有存在以下情况时才提问，一道题一道题提交，使用 AskUserQuestion 工具：**

**触发条件与问题设计：**

**问题1：分析范围确认（当检测到分期/子系统迹象时）**

```
问题：我注意到文档中提及"V1.0"/"后续版本"/"与主系统对接"等表述，请确认分析范围：

选项：
A. 仅分析当前 PRD 的完整性
B. 这是分期项目，当前是第 ___ 期，请结合项目整体规划分析
C. 这是子功能模块，请结合主系统进行全面分析（需提供相关文档）
D. 其他：______
```

**问题2：引用文件处理（当检测到外部引用时）**

```
问题：文档中引用了以下外部文件，是否授权获取以进行更全面的分析？

选项：
A. 授权获取全部引用文件
B. 选择性获取：______
C. 仅分析当前文档
D. 其他：______
```

**问题3：行业背景确认（当无法从文档确定行业时）**

```
问题：无法从文档中明确识别所属行业，请确认以便进行针对性分析：

选项：
A. 金融科技
B. 电商零售
C. 企业服务/SaaS
D. 医疗健康
E. 教育培训
F. 其他：______
```

**问题4：合规要求确认（当涉及敏感行业时）**

```
问题：该产品是否有特殊的合规或监管要求需要关注？

选项：
A. 无特殊合规要求
B. 等保2.0（等级保护）
C. GDPR（欧盟数据保护）
D. 金融合规（银保监会/证监会要求）
E. 医疗合规（HIPAA/医疗器械注册）
F. 其他：______
```

**提问原则：**
- 一次只问一个问题
- 优先使用多选题 + 自填选项
- 如果文档完整且明确，跳过提问直接进入分析

### 阶段4：引用文件处理（如需）

对于用户授权的引用文件：
- 询问用户提供文件位置或直接上传
- 尝试读取文件内容
- 合并到分析上下文
- 递归深度由 AI 自主判断（通常 Level 1-2）

### 阶段5：深度分析引擎

**参考 `references/analysis-frameworks.md` 获取详细分析框架。**

#### 5.1 逻辑矛盾检测

**理论基础：** 形式逻辑（矛盾律、排中律）、需求工程不一致检测

**检测规则：**

| 规则类型 | 检测公式/方法 | 说明 |
|---------|-------------|------|
| 互斥条件冲突 | A ∧ ¬A → ⊥ | 同一条件下两个需求不能同时满足 |
| 方向性矛盾 | ∂f/∂x > 0 ∧ ∂f/∂x < 0 | A 要求增加指标 X，B 要求减少指标 X |
| 因果倒置 | Cause → Effect 检验 | 验证因果链条的正确性 |
| 边界条件矛盾 | ∀x ∈ [a,b]: P(x) 一致性 | 同一边界在多处定义是否一致 |
| 度量标准矛盾 | Unit(A) ≠ Unit(B) | 同一指标使用不同度量标准 |

**矛盾严重度评估：**

```
严重度 = (影响范围) × (修复成本) × (发现阶段)

影响范围：高(3) / 中(2) / 低(1)
修复成本：高(3) / 中(2) / 低(1)
发现阶段：需求(1) / 设计(2) / 开发(3) / 测试(4) / 上线(5)

严重度 ≥ 12：🔴 关键矛盾
严重度 6-11：🟡 中等矛盾
严重度 ≤ 5：🟢 轻微矛盾
```

#### 5.2 遗漏场景检测

**理论基础：** 场景分析法、ISO 25010 质量模型、边界值分析（BVA）

**场景覆盖矩阵：**

```
场景空间 = [用户角色] × [操作类型] × [系统状态] × [时间条件]

覆盖度 = Σ(已覆盖场景) / Σ(理论场景总数)

< 30%：🔴 严重遗漏
30-60%：🟡 中度遗漏
> 60%：🟢 基本完整
```

**检测维度（ISO 25010）：**

| 质量属性 | 子属性 | 检测要点 |
|---------|-------|---------|
| 功能性 | 完备性、正确性、适用性 | 功能是否覆盖所有业务场景 |
| 性能效率 | 时间特性、资源利用率 | 响应时间、吞吐量、资源消耗 |
| 兼容性 | 共存性、互操作性 | 与其他系统的集成能力 |
| 可用性 | 可辨识性、可操作性、用户差错防范 | 用户学习成本、操作便利性 |
| 可靠性 | 成熟度、可用性、容错性、可恢复性 | 系统稳定性、故障恢复能力 |
| 安全性 | 保密性、完整性、不可否认性、可审计性 | 数据保护、访问控制 |
| 维护性 | 模块性、可重用性、可分析性、可修改性 | 代码可维护性 |
| 可移植性 | 适应性、可安装性、可替换性 | 跨平台能力 |

**边界值分析（BVA）：**

```
对于每个输入变量，检测是否覆盖：
- 最小值
- 最小值-1（无效边界）
- 最大值
- 最大值+1（无效边界）
- 正常值
```

#### 5.3 优先级冲突检测

**理论基础：** MoSCoW 框架、Pareto 法则（80/20）、项目铁三角

**MoSCoW 分布检测：**

```
理想比例：Must : Should : Could : Won't ≈ 60 : 20 : 15 : 5

IF Must-Have > 60% → ⚠️ "Must-Have 超载，建议重新评估优先级"
IF Must-Have < 40% → ⚠️ "核心需求可能不足"
```

**Pareto 验证：**

```
核心需求价值占比 = Σ(Top 20% 需求的价值) / Σ(所有需求价值)

理想值：≥ 80%
IF < 70% → ⚠️ "需求价值分布过于分散"
```

**项目铁三角平衡检测：**

```
三角失衡检测：
IF (时间约束 = "硬性") AND (质量约束 = "硬性") AND (范围约束 = "硬性")
THEN → 🔴 "项目铁三角失衡，至少需要放宽一个约束"

推荐：使用"不可能三角"理论向用户解释权衡必要性
```

**依赖图分析：**

```
构建需求依赖图 G = (V, E)
V = 需求集合
E = 依赖关系

IF ∃ 边 (低优先级 → 高优先级)
THEN → ⚠️ "存在依赖倒置，低优先级需求是高优先级的前置条件"
```

#### 5.4 隐含假设提取

**理论基础：** 假设映射法、批判性思维框架、风险矩阵

**假设类型与检测：**

| 假设类型 | 检测触发词 | 验证方法 |
|---------|-----------|---------|
| 技术假设 | "假设"、"预计"、"预期" | 技术可行性评估 |
| 用户行为假设 | "用户会"、"通常"、"一般" | 用户研究验证 |
| 业务环境假设 | "市场"、"竞品"、"法规" | PESTEL 分析 |
| 数据假设 | "数据"、"历史"、"格式" | 数据就绪度评估 |
| 资源假设 | "团队"、"人员"、"依赖" | 能力成熟度评估 |
| 时间假设 | "预计"、"估计"、"周期" | 关键路径法（CPM） |

**假设风险评估公式：**

```
假设风险值 = P(假设不成立) × I(假设失败影响) × D(检测难度)

P（概率）：高(3) / 中(2) / 低(1)
I（影响）：高(3) / 中(2) / 低(1)
D（检测难度）：难(3) / 中(2) / 易(1)

风险值 ≥ 18：🔴 关键假设（必须验证）
风险值 9-17：🟡 中等假设（建议跟踪）
风险值 ≤ 8：🟢 可容忍假设
```

#### 5.5 技术兼容性分析

**理论基础：** CAP 定理、技术债务模型、系统集成理论

**分析维度：**

| 维度 | 检测方法 | 理论依据 |
|-----|---------|---------|
| 技术选型合理性 | 技术栈与业务场景匹配度分析 | 康威定律、技术适配性理论 |
| 版本兼容性 | 依赖库版本检查、EOL 检测 | 软件生命周期管理 |
| 架构一致性 | 与现有架构风格对比 | 架构风格理论 |
| 扩展性评估 | 负载增长预测 | Amdahl 定律、可扩展性设计原则 |
| 安全合规 | OWASP Top 10、等保2.0、GDPR | 安全标准框架 |

**CAP 定理应用：**

```
对于分布式系统：
- C（一致性）+ A（可用性）+ P（分区容错性）最多满足两个

IF 文档要求"强一致性" AND "高可用" AND "分布式部署"
THEN → ⚠️ "CAP 定理约束，需明确权衡策略"
```

#### 5.6 前沿技术补充建议

**触发条件：** 文档提及相关技术领域

**建议框架：**

```
基于文档描述的 [技术领域]，以下前沿技术可能增强方案：

1. [技术名称]
   - 当前方案：[文档描述]
   - 建议升级：[前沿技术方案]
   - 价值：[量化或质化价值]
   - 参考：[权威来源：Gartner/IDC/IEEE/ACM]
```

**技术成熟度评估（TRL）：**

```
TRL 1-3：基础研究阶段
TRL 4-6：技术开发阶段
TRL 7-9：系统部署阶段

建议：优先考虑 TRL ≥ 7 的成熟技术，TRL < 7 的技术需评估风险
```

## 关键原则

- **先理解后提问**：完整阅读文档后再提问，不预设问题
- **一次一题**：使用 AskUserQuestion 工具，一道题一道题提交
- **多选优先**：提供选项 + 自填选项，降低用户输入成本
- **理论支撑**：每个分析维度都有科学理论或方法论支撑
- **量化评估**：使用公式和评分系统，避免主观判断
- **文件输出**：必须使用 Write 工具将报告写入 MD 文件，不能只在对话中展示
