# 分层需求细化与追踪

按目标到细节逐层拆解复杂需求，建立需求编号、决策记录和双向追踪。

| 项目 | 内容 |
|---|---|
| 分类 | 产品与需求 |
| 适合什么时候 | 复杂需求需要递归细化、跨模块一致性、SRS或RTM时使用；简单想法优先一句话需求拆解。 |
| 需要提供 | 复杂产品想法、初步PRD或功能模块 |
| 可以得到 | 分层需求规格、需求追踪矩阵与验收清单 |
| 能力说明 | 方法可用；原版配套缺失 |
| 兼容调用标识 | `$requirements-fractal` |

## 直接这样说

> 请用分层需求细化与追踪，将这份需求拆到可验收层级，并建立需求追踪矩阵。

## 核心方法

1. 从用户描述或已有材料建立L0目标与范围，使用单一总文档记录日期、版本和未决项。
2. 逐层拆解：L1功能模块 → L2子功能与场景 → L3具体需求与验收 → 必要时L4字段、规则及交互细节。横向模块职责清晰，避免重复。
3. 每层都检查目标、边界、决策、依赖与验收，再保存成果。停止于足够实现与验证的颗粒度，不为形式继续递归。
4. 对会影响产品方向的未决选择提供稳健、平衡、创新方案，说明收益、成本和风险；用户已有选择则记录并继续，不强制每项三选一。
5. 技术选择服务于用户需求，需涉及新技术时核查官方资料。将实际决策、时间和理由关联REQ编号。
6. 每条需求至少有：REQ-ID、上层目标、描述、用户场景、优先级、依赖、可验证验收标准和状态。RTM关联需求、设计、测试与决策。
7. 验证需求到文档的覆盖、文档到需求的依据、跨层一致性和单条无歧义；修复后复查受影响项。仅在当前任务授权且适用时并行，否则顺序完成，不假装已获独立复核。
8. 交付SRS、RTM与需求清单，必要时合并在同一文档；原文中的上下游技能只作体系说明，不自动创建额外项目。

## 安装与能力边界

缺少三份模板与验证参考，以及原文列举的上下游技能；用本文内置输出结构和当前可用能力完成。

安装包通过结构检查不等于完整功能已经实测。调用时还会检查文档、图像、语音等实际工具。界面名称为中文，内部标识和 SKILL.md、agents/openai.yaml 等必要文件名保留标准格式。
