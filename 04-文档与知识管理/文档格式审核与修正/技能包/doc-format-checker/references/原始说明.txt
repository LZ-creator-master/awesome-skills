# doc-format-checker

Word文档格式自动审核、修改与查看工具。整合了 `docx-reader` 的文档查看能力，支持完整的"查看→审核→修改→报告"工作流。

## 功能

### 文档查看（基于 docx-reader）
- **全文读取**：提取完整文本内容，支持数学公式（OMML→LaTeX）
- **图片提取**：提取文档中所有嵌入的图片（PNG、JPEG、EMF等）
- **页面渲染**：将文档转为PDF后逐页截图，用于可视化查看排版效果
- **Pandoc转换**：通过Pandoc提取Markdown格式文本（保留标题、列表、表格结构）

### 格式审核与修改
- **自动识别**：通过正则表达式匹配文本模式，自动识别一级标题（第X章、一、XXX等）、二级标题（X.X）、三级标题（X.X.X）、图注（图 X.X）、表注（表 X.X）
- **格式修改**：自动应用正确的Word样式，包括字体、字号、段落间距、行距等
- **格式审核**：仅检查并报告格式问题，不修改文档
- **黄色高亮**：修改处自动添加黄色高亮标注
- **页码定位**：通过PDF转换获取每个修改项的精确页码
- **修改报告**：生成详细的Word格式修改报告，包含页码信息

### AI内容审核与修改（新增）
- **智能分析**：调用AI能力，自动扫描文档内容
- **通用审核**：根据用户要求，审核任意类型的格式问题
  - 数值与单位空格（如 100℃ → 100 ℃）
  - 中英文/数字间空格（如 Figure1 → Figure 1）
  - 标点符号规范（如全角括号→半角括号）
  - 术语统一（如"传感器"/"传感元件"统一）
  - 其他自定义要求
- **自动修改**：直接修改文档内容，标注修改处
- **修改报告**：输出修改报告，记录所有变更

## 使用方式

### 完整工作流（推荐）

当用户需要修改或审核Word文档格式时，按以下步骤操作：

**步骤1：查看文档**
```bash
python scripts/read_docx.py <input.docx> <output_dir>
```
生成文件：
| 文件 | 说明 |
|------|------|
| `content.md` | 全文文本 + LaTeX公式 |
| `content_pandoc.md` | Pandoc转换的Markdown |
| `images/` | 所有嵌入图片 |
| `pages/` | 逐页渲染截图（用于可视化检查） |
| `metadata.json` | 文档元数据摘要 |

**步骤2：读取并理解文档内容**
- 读取 `content.md` 了解全文内容和结构
- 查看 `pages/` 目录下的页面截图确认排版效果
- 识别文档各部分（封面、摘要、正文、附录等）

**步骤3：审核或修改格式**
```bash
# 修改模式（自动应用样式 + 黄色高亮）
python scripts/doc_formatter.py <input.docx> -o <output.docx>

# 审核模式（仅检查，不修改）
python scripts/doc_formatter.py <input.docx> --mode audit

# 使用自定义配置
python scripts/doc_formatter.py <input.docx> --config format_config.json

# 不添加黄色高亮
python scripts/doc_formatter.py <input.docx> --no-highlight
```

**步骤4：获取页码**
```bash
python scripts/get_page_numbers.py <output.docx> <modifications.json>
```

**步骤5：生成报告**
```bash
node scripts/generate_report.js <modifications.json> -o <report.docx>
```

**步骤6：验证修改效果（重要）**

修改完成后，必须验证修改是否真正生效：

```bash
# 方法1：提取文本查看
python scripts/read_docx.py <output.docx> <output_review_dir>
cat <output_review_dir>/content.md

# 方法2：直接查看XML结构
unzip -p <output.docx> word/document.xml | grep -A2 -B2 "关键文本"

# 方法3：生成页面截图对比
# 对比 <output_dir>/pages/ 和 <output_review_dir>/pages/ 中的截图
```

**验证要点**：
- 检查 `content.md` 中的文本是否符合预期（如 "250 ℃" 而非 "250℃"）
- 对于跨 run 的修改，确认 XML 中相关内容已合并到同一 run
- 对比修改前后的页面截图，确认格式变化正确显示

**常见验证失败原因**：
- 跨 run 修改时未合并到同一 run（Word 不显示空格）
- XML 命名空间处理错误
- 文件被 Word 占用导致写入失败

### 快速模式

如果已经了解文档结构，可以直接运行步骤3-5，但**强烈建议执行步骤6进行验证**。

## 脚本说明

### scripts/read_docx.py
文档查看脚本（来自 docx-reader），4步提取管道：
1. Pandoc → Markdown（含LaTeX数学公式）
2. XML解析器 → OMML公式 → LaTeX
3. 图片提取 → word/media/ 中的所有图片
4. 页面渲染 → PDF → 逐页JPEG截图

### scripts/doc_formatter.py
核心格式处理脚本，支持两种模式：
- `--mode fix`：修改文档格式（默认）
- `--mode audit`：仅审核，不修改
- `--config <file>`：指定格式配置JSON文件
- `--no-highlight`：不添加黄色高亮
- `-o <file>`：指定输出文件路径

### scripts/get_page_numbers.py
页码获取脚本，通过PDF转换和段落映射获取精确页码。

### scripts/generate_report.js
报告生成脚本，使用docx-js生成带页码的Word格式修改报告。

### scripts/ai_doc_reviewer.py
AI内容审核与修改脚本，调用AI能力自动审核并修改文档内容：
- `-r <要求>`：指定审核要求，如"数值与单位之间需要空一格"
- `--dry-run`：仅分析不实际修改
- `-o <file>`：指定输出文件路径

示例：
```bash
# 数值与单位空格
python scripts/ai_doc_reviewer.py input.docx -o output.docx -r "数值与单位之间需要空一格"

# 全角括号改半角
python scripts/ai_doc_reviewer.py input.docx -r "全角括号改为半角括号"

# 术语统一
python scripts/ai_doc_reviewer.py input.docx -r "术语'传感器'统一，不要混用'传感元件'"
```

## 配置文件格式（可选）

通过 `--config` 参数指定JSON配置文件，自定义识别规则和样式：

```json
{
  "heading_patterns": {
    "1": ["^引言$", "^结论$", "^第[一二三四五六七八九十百]+章\\s*.+"],
    "2": ["^\\d+\\.\\d+\\s+.+"],
    "3": ["^\\d+\\.\\d+\\.\\d+\\s+.+"]
  },
  "caption_patterns": ["^图\\s*\\d+\\.\\d+\\s+.+", "^表\\s*\\d+\\.\\d+\\s+.+"],
  "styles": {
    "1": { "font": "黑体", "size": 32, "before": 0, "after": 0, "line": 360 },
    "2": { "font": "黑体", "size": 24, "before": 160, "after": 160, "line": 240 },
    "3": { "font": "黑体", "size": 24, "before": 0, "after": 160, "line": 360 },
    "caption": { "font": "宋体", "size": 22 }
  }
}
```

## 模糊需求确认机制（重要）

在执行格式修改之前，如果遇到以下任何一种模糊或不清晰的情况，**必须暂停执行，使用 AskUserQuestion 工具向用户确认**，得到明确答复后再继续处理。

### 需要确认的场景

#### 1. 格式要求不完整
**触发条件**：用户提供的格式要求文件中缺少某些部分的格式规范。
**确认内容**：
- "格式要求中未提及【正文/图注/参考文献/页眉页脚】的格式，这些部分如何处理？"
- 选项：A) 按正文格式处理  B) 保持原格式不变  C) 用户补充要求

#### 2. 文档结构不明确
**触发条件**：文档中某些部分的样式分类不清晰（如某段文本可能是标题也可能是正文）。
**确认内容**：
- "以下内容无法自动判断分类：【引用文本内容前30字...】，请问这应该是？"
- 选项：A) 一级标题  B) 二级标题  C) 正文  D) 其他

#### 3. 标题加粗规则不明确
**触发条件**：格式要求中说"黑体X号"但未明确是否需要额外加粗标记。
**确认内容**：
- "格式要求中标题使用黑体，是否需要额外添加加粗标记？"
- 选项：A) 黑体不加粗（推荐）  B) 需要加粗标记

#### 4. 特殊部分处理方式
**触发条件**：不确定封面、摘要、致谢、附录等部分是否需要格式修改。
**确认内容**：
- "【封面/摘要/致谢/附录】部分是否需要按照格式要求修改？"
- 选项：A) 保持原格式不变  B) 按正文格式修改  C) 有特殊要求

#### 5. 识别结果存疑
**触发条件**：自动识别结果中存在可能误判的项（如正文中出现类似标题格式的文本）。
**确认内容**：
- "以下内容被识别为【X级标题】，但可能存在误判：【文本前30字...】，是否正确？"
- 选项：A) 识别正确，继续处理  B) 跳过此项  C) 归类为其他样式

#### 6. 高亮标注范围
**触发条件**：不确定用户希望哪些修改需要高亮标注。
**确认内容**：
- "您希望哪些修改处添加黄色高亮标注？"
- 选项：A) 仅标题  B) 标题和图注  C) 所有修改处  D) 不需要高亮

#### 7. 修改范围确认
**触发条件**：首次处理新文档时，识别结果可能超出预期。
**确认内容**：
- "已识别到【X】处需要修改（1级标题X个、2级标题X个、3级标题X个、图注X个），确认执行？"
- 选项：A) 全部执行  B) 仅修改标题  C) 仅修改图注  D) 让我选择

### 确认流程

```
开始处理
    ↓
查看文档结构 → 读取格式要求
    ↓
是否存在模糊情况？──是──→ 向用户提问确认 ──→ 获得明确答复
    ↓ 否                                    ↓
执行格式修改 ←──────────────────────────────┘
    ↓
生成报告
```

### 确认原则

1. **宁可多问一次，不要错误修改**：格式修改影响全文，错误的修改比不修改更难恢复
2. **每次最多问2-3个问题**：不要一次性问太多，分批确认
3. **提供合理默认值**：在选项中标注推荐选项，降低用户决策成本
4. **记录用户选择**：同一文档的后续处理中，不再重复确认已回答的问题

## Word XML 结构经验总结（重要）

### 核心认知

Word文档的 `.docx` 文件本质上是 ZIP 压缩包，内部的 `word/document.xml` 使用 XML 结构存储内容。**理解 XML 结构是正确修改 Word 文档的关键**。

### 关键概念：Run（`<w:r>`）和 Text（`<w:t>`）

在 Word XML 中，文本内容被组织为：

```xml
<w:p>  <!-- 段落 -->
  <w:r>  <!-- Run：格式相同的文本块 -->
    <w:rPr>...</w:rPr>  <!-- 格式属性 -->
    <w:t>文本内容</w:t>  <!-- 实际文本 -->
  </w:r>
</w:p>
```

**重要发现**：Word 渲染时，**不同 run 之间的空格不会显示**。例如：

```xml
<!-- 错误做法：数字和单位在不同 run 中 -->
<w:r><w:t>250 </w:t></w:r>  <!-- 有空格，但Word不渲染 -->
<w:r><w:t>℃</w:t></w:r>

<!-- 正确做法：数字和单位在同一个 run 中 -->
<w:r><w:t>250 ℃</w:t></w:r>  <!-- 空格正常显示 -->
```

### 实际案例：数值与单位空格

**问题场景**：原文档中 "250℃" 的 XML 结构：

```xml
<w:r>
  <w:t>250</w:t>  <!-- 数字在一个 run -->
</w:r>
<w:r>
  <w:t>℃</w:t>    <!-- 单位在另一个 run -->
</w:r>
```

**错误修改**：只在第一个 run 的文本末尾加空格

```xml
<w:r>
  <w:t>250 </w:t>  <!-- 加了空格，但Word不渲染 -->
</w:r>
<w:r>
  <w:t>℃</w:t>
</w:r>
```

**正确修改**：将单位合并到同一个 run 中

```xml
<w:r>
  <w:t>250 ℃</w:t>  <!-- 数字、空格、单位在同一 run，正确显示 -->
</w:r>
<w:r>
  <w:t></w:t>       <!-- 原单位 run 清空或删除 -->
</w:r>
```

### 通用处理原则

| 场景 | 处理方式 |
|------|----------|
| **同 run 内修改** | 直接替换 `<w:t>` 中的文本内容 |
| **跨 run 修改** | 必须将相关内容合并到同一个 run 中 |
| **添加高亮** | 在 `<w:rPr>` 中添加 `<w:shd w:fill="FFFF00" w:val="clear"/>` |
| **修改样式** | 修改 `<w:pPr>` 中的 `<w:pStyle>` 或 `<w:rPr>` 中的格式属性 |

### 调试技巧

1. **查看原始 XML 结构**
   ```bash
   unzip -p input.docx word/document.xml | python -c "import sys; print(sys.stdin.read()[:5000])"
   ```

2. **验证修改后的结构**
   ```bash
   unzip -p output.docx word/document.xml | grep -A2 -B2 "250"
   ```

3. **检查文本提取结果**
   ```bash
   python scripts/read_docx.py input.docx output_dir/
   cat output_dir/content.md
   ```

### 常见陷阱

| 陷阱 | 说明 | 解决方案 |
|------|------|----------|
| 跨 run 空格不显示 | 不同 run 之间的空格 Word 不渲染 | 合并到同一 run |
| XML 命名空间 | Word XML 使用命名空间，必须使用完整标签名 | 使用 `{namespace}tag` 格式 |
| 文件被占用 | Word 打开时无法写入 | 关闭 Word 后重试或使用新文件名 |
| 特殊字符编码 | 中文、℃等特殊字符需要 UTF-8 编码 | 确保读写都使用 UTF-8 |

## 注意事项

- 修改前建议先用 `read_docx.py` 查看文档，确认文档结构和内容
- 封面、摘要、致谢等特殊部分默认保持原格式不变（除非用户确认需要修改）
- 黑体标题不额外加粗（黑体本身已是粗体）
- 页码通过段落位置映射估算，可能存在±1页的偏差
- 遇到任何不确定的情况，优先向用户确认而非自行猜测
- **修改后务必验证 XML 结构和文本提取结果，确保修改真正生效**
